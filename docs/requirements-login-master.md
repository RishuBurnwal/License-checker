## Summary

The product currently logs an admin in with three visible inputs — `tenant`, `username`, `password` — resolved by `service.authenticateAdmin(tenant, username, password)` through `repository.getAdminByTenantAndUsername` (`worker/src/service.ts:70-73`, `worker/src/repository.ts:908`, `worker/src/routes.ts:35/40`). On failure it returns `401 "Invalid tenant, username or password"` and, for a disabled tenant_admin, `403 "Tenant is disabled"` (`worker/src/service.ts:74-81`). Tenancy pervades the stack: a `tenants` table + default row id 1 seeded by `migrations/0003_add_tenants.sql`, `tenant_id` columns on `apps` and `admin_users`, tenant triggers (`trg_apps_tenant_required_insert/update`) and tenant indexes (`idx_admin_users_tenant`, `idx_apps_tenant_created`); `resolveTenantId` reading the `X-Tenant-Id` header (`worker/src/middleware.ts:71-84`); `/api/admin/tenants` routes (`worker/src/routes.ts:75-132`) gated by `requireSuperAdmin` (`middleware.ts:52`); tenant service methods and repository SQL (`service.ts createTenant/updateTenant/updateTenantStatus/resetTenantAdminPassword/deleteTenant`, `repository.ts:159/908/977`); constants/types (`constants.ts:9 TENANT_STATUS`, `:19-24 ADMIN_ROLE super_admin/tenant_admin`, `:253 isTenantStatus`; `types.ts TenantRow`, `tenant_id`/`tenant_status`/`tenant_name` fields); the admin console tenant field, Tenants menu/page, hooks and i18n (`admin/src/components/Login.tsx`, `admin/src/routes.tsx`, `admin/src/pages/TenantsPage.tsx`, `admin/src/types.ts`, `admin/src/i18n/messages.ts`); and the launcher printing `tenant: default` (`main.py:317`). The measured tenant/slug surface (case-insensitive, `memory/fix-plan.md §4b`): worker/src 374, admin/src 115, migrations 26, docs 127, scripts 26, license-checker/src 0.

Two role axes exist today: a login role `admin_users.role` (`super_admin`/`tenant_admin`, CHECK from `migrations/0003`) and a management role `admin_users.user_role` (`admin`/`staff`, from `migrations/0008`) — see `worker/src/constants.ts:19-36` and `worker/src/middleware.ts:67-70` (`isUserManager` = `role === super_admin || user_role === 'admin'`).

The required end state:

- Multi-tenancy is REMOVED COMPLETELY. No `tenant` or `slug` token exists anywhere in shipped code, migrations, types, i18n, or docs. The `tenants` table is dropped; `tenant_id` is removed from `apps` and `admin_users`; tenant triggers and indexes are dropped; dashboard/apps/codes/logs/users/sessions queries become GLOBAL (D-A, final).
- The login `role` axis (`super_admin`/`tenant_admin`) is retired because `tenant_admin` is tenant wording and `super_admin`'s only distinguishing power (tenant management) is deleted; management is governed solely by `user_role` (`admin`/`staff`) plus the master-password login model (D-A.2 resolution, see AC-A11 and decision D-24).
- Login gains a "Login as" dropdown with two options, Admin and User, driving the field count (3 vs 2); the SERVER enforces role and master-password rules purely from the stored account, never from the dropdown (D-B).
- One global master password is introduced, stored as a PBKDF2 hash AND its salt in a settings table (new migration 0009 creates the table; the hash is seeded in a code bootstrap, not in SQL), with its initial value coming from a new optional seed var `ADMIN_MASTER_PASSWORD`, and changeable from console settings (D-B).

Behaviour changes must stay green against the existing suites (minus the tenant tests, which are removed/rewritten) and add new tests plus a Playwright Chromium end-to-end pass. ## Functional Requirements

- FR-1 Remove multi-tenancy completely from the database: DROP the `tenants` table and remove `tenant_id` from `apps` and `admin_users` via additive migrations `0010` (rebuild `apps`), `0011` (rebuild `admin_users`), and `0012` (`DROP TABLE tenants`) — distinct from the additive `0009` that creates the `settings` table (see M-1 resolution); preserve all non-tenant data. Dashboard/apps/codes/logs/users/sessions become global (no tenant scoping). (D-A)
- FR-2 Remove all tenant handling from the Worker: delete `resolveTenantId`, `X-Tenant-Id` handling, `requireSuperAdmin` tenant logic, all `/api/admin/tenants` routes, tenant service methods, tenant repository SQL, and tenant fields on types. Login must not require, send, or accept `tenant` at all; the server resolves the account by its globally-unique username alone (`getAdminByUsername`, `worker/src/repository.ts:896`), with username uniqueness verified and enforced. (D-A)
- FR-3 Retire the login `role` axis: migrate any remaining `tenant_admin` rows and remove the `role` column (and its `super_admin`/`tenant_admin` CHECK) so no tenant wording remains; `user_role` (`admin`/`staff`) becomes the sole role axis, coherent with the master-password login model. (D-A.2, see decision D-24)
- FR-4 Remove all tenant surface from the admin React app: the tenant field in `Login.tsx`, the tenant menu entry/switcher/header, all tenant pages/components/hooks/types, and every tenant string in `admin/src/i18n/messages.ts`. (D-A)
- FR-5 Add a "Login as" dropdown (Admin / User) to the login form that controls whether a Master Password field is shown (Admin: 3 fields; User: 2 fields). (D-B)
- FR-6 The server authorises purely by the stored account role (`user_role`), never by the submitted dropdown value; master-password rules are enforced server-side. (D-B)
- FR-7 Introduce one global master password, stored as a PBKDF2 hash AND its salt in a settings table. Migration 0009 only CREATES the settings table; the hash is seeded once in a code bootstrap (analogous to `ensureBootstrapAdmin`, `worker/src/service.ts:50`) when the settings row is absent, taking its initial value from a new optional seed var `ADMIN_MASTER_PASSWORD`. (D-B)
- FR-8 Let an admin change the global master password from console settings (current master + new master) via `PATCH /api/admin/settings/master-password` gated by `requireUserManager`, surfaced in a new `SettingsPage.tsx` (full contract pinned in AC-B12). After a change the DB-stored hash is authoritative; the seed var is never re-read to override it. (D-B)
- FR-9 Extend the admin reset tooling (`scripts/reset-admin.mjs` / `python main.py --reset-admin`) to also reset the master password hash to the dev default `master`, writing the hash directly (reset-script path), bypassing the console min-length rule. (D-B)
- FR-10 Let an admin set any user's password directly, with a "require change on next login" checkbox defaulting ON; when OFF, the next login is NOT forced through the change flow. (D-C)
- FR-11 Let an admin generate a crypto-strong random password (≥16 chars) shown once with copy, applied to the target user, never stored or logged in plaintext. (D-C)
- FR-12 Preserve existing user-management capabilities (create user, list, kick) and keep staff denied server-side. (D-C)
- FR-13 The launcher prints Admin credentials (admin/admin, first login forces change, master `master`) and User credentials (username + password only), with no tenant line, without regressing Run/Build/Update or the Wrangler env/timeout handling. (D-D)

## Non-Functional Requirements

- NFR-1 No new plaintext secret is stored or logged. The master password and any generated user password exist in plaintext only transiently in a single request/response. "No plaintext" refers to the master-password/user-password plaintext, NOT the PBKDF2 salt (the salt is not secret and MUST be persisted — see AC-B9/M1). The ONLY permitted plaintext exposure of a generated password is the single response field defined in AC-C4; it is never written to the DB, server logs, log messages, URLs, or committed files (AGENTS.md Non-Negotiable Constraints; `worker/src/crypto.ts` PBKDF2 pattern).
- NFR-2 Credential comparisons use the existing timing-safe path (`verifyPassword` → `timingSafeEqual`, `worker/src/crypto.ts:88-91`); the master-password check must use the same path.
- NFR-3 Authentication failures are non-enumerating: wrong username, wrong password, and wrong/missing master password (for an admin account) all return the SAME generic 401 with the SAME body and no field-specific hint, and with NO tenant wording. Because the dropdown value is never read server-side (AC-B4), there is no "role/dropdown mismatch" failure for a staff account to leak.
- NFR-4 Migrations are additive and never edit published migrations 0001–0008 (confirmed newest is `migrations/0008_add_admin_users_and_sessions.sql`, `memory/fix-plan.md §2`). Each NEW migration file has exactly one job (resolves M-1): `0009` CREATES the `settings` table only (additive, CREATE only, no DROP/rebuild); `0010` rebuilds `apps`; `0011` rebuilds `admin_users`; `0012` drops `tenants`. The destructive tenant removal (`0010`–`0012`) uses the SQLite 12-step table rebuild (new table without the column, copy data, drop old, rename, recreate ONLY the non-tenant indexes/triggers) in the pinned order of AC-A1; it never edits a published migration. Schema changes stay in `migrations/` and SQL stays in `repository.ts` with bound parameters (AGENTS.md).
- NFR-5 The pre-existing green baseline is preserved for all NON-tenant behaviour: worker, admin, and checker suites all stay passing (after tenant tests are removed/rewritten per AC-A10), and `pnpm type-check` / `pnpm build` succeed. The exact baseline counts MUST be re-confirmed from a fresh run (the two figures in `memory/fix-plan.md` disagree) before being used as a gate.

- AC-B9 There is exactly ONE global master password (not per-account), stored as a PBKDF2 hash AND its random salt (reusing `hashPassword`, which returns `{ hash, salt }` with a per-call random salt, `worker/src/crypto.ts:69`) in a `settings` table. **(Resolves M1 + N3.)** Migration 0009 only CREATES the `settings` table with the pinned shape `settings(key TEXT PRIMARY KEY, value TEXT NOT NULL, updated_at TEXT)` (verified: no `settings` table exists in `migrations/0001`–`0008`); the master hash and salt are persisted as two rows — `master_password_hash` and `master_password_salt` (both non-secret-salt + secret-hash; the plaintext master password is NEVER a stored value). The migration does NOT and cannot compute the hash. ON CONFLICT(key) DO UPDATE SET value = excluded.value, updated_at = excluded.updated_at`). No `settings` SQL appears in `service.ts` or `routes.ts`; every read/write of `master_password_hash`/`master_password_salt` goes through these two accessors.

The pinned dev value is the literal `master` (NOT a `randomSecret()`), so the stored hash matches the credential the launcher prints (AC-D1) and the reset default (AC-B14).

## Assumptions

- A single global master password (two rows — hash + salt — in a `settings` table) satisfies "ek master password"; the master password is required IN ADDITION to the admin's own password, not as a replacement.
- With the login `role` axis retired (AC-A11), "Admin" in the login dropdown maps to the surviving manager definition `user_role === 'admin'`; "User" maps to a staff account. The server authorises on the stored `user_role` only; the dropdown is a UI hint.
- The former bootstrap `super_admin` account has no distinguishing power once tenant routes are deleted, so collapsing it to `user_role='admin'` loses no capability (verified: `requireSuperAdmin` is only used by the deleted `/api/admin/tenants` routes, `fix-plan.md §4`).
- The forced-change flow reuses the existing `must_change_password` column and `PASSWORD_CHANGE_EXEMPT_PATHS` mechanism (`worker/src/middleware.ts`); no new forced-change machinery is introduced.
- The master-password console change rule is ≥8 chars (reusing the `validateNewPassword` minimum); the dev literal `master` (6 chars) is a reset-script-only seed that bypasses that rule, exactly as the `admin/admin` bootstrap does (AC-B12/AC-B14).
- The base64url charset of `generateRandomToken` passes `validateNewPassword` (length ≥ 16 ≥ 8, no complexity requirement beyond length — confirmed `validateNewPassword` only checks `length < 8`, `service.ts:1456-1460`). The implementer must re-confirm this if `validateNewPassword` gains complexity rules.
- The 12-step `admin_users` rebuild (migration `0011`) preserves the `username` global UNIQUE constraint and the `admin_sessions.admin_id` / `activation_batches.created_by` / `activation_codes.created_by` foreign-key relationships; only `tenant_id` and `role` columns and their tenant indexes are dropped. The FK/transaction strategy is no longer deferred to the implementer (resolves M-2): the rebuild order is pinned (`0010` `apps`, then `0011` `admin_users`, then `0012` `DROP TABLE tenants`) and each rebuild migration begins with `PRAGMA defer_foreign_keys = ON;` because `wrangler d1 migrations apply` runs each migration in an implicit transaction where `PRAGMA foreign_keys = OFF` is a no-op (see AC-A1). The implementer still confirms the exact child-FK list against the live schema before writing the rebuild, but the mechanism and ordering are fixed here, not left open.
